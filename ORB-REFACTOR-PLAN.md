# ORB Server-Authoritative — состояние и порядок выката

> Обновлено: 2026-09-05. Клиентская часть **сделана**, SQL **готов, но не применён**.
> Парный файл: `supabase-orb-authoritative.sql` (версия 3.0).

---

## Зачем

`players.orb` писался клиентом напрямую, а anon-ключ лежит внутри APK. Аудит
2026-09-05 на живой базе: верхний аккаунт — 1 082 663 328 ORB при нуле платежей,
то есть без Founder-множителя и без покупных рефиллов. Честный потолок такого
аккаунта — 2,9 млн в сутки, значит на этот баланс нужен 371 день безупречной
игры. Аккаунт был активен три дня.

При курсе 10 000 ORB = 1 SKORA верхняя восьмёрка — это ~233 000 SKORA, а
`tournament_scores` решает раздачу реальных SOL.

---

## Что сделано в клиенте

Июньский план предлагал переписать ~30 мест вида `setOrb(next); syncScore(next)`.
Этого не понадобилось: `syncScore` — **единственная** точка, где баланс уходит
на сервер, а `scheduleSyncScore` уже батчит тапы по 5 секунд. Достаточно было
переделать её с «записать абсолютное значение» на «предложить дельту».

| Файл | Что изменилось |
|------|----------------|
| `lib/orb.ts` | новый — `applyOrbDelta`, `fetchOrbBalance` |
| `App.tsx` | `syncScore` шлёт дельту через RPC; `level`/`streak` остались прямой записью |
| `App.tsx` | `syncedOrbRef` — база отсчёта, читается с сервера при старте |
| `App.tsx` | `syncInFlightRef` — два параллельных вызова не отправят одну дельту дважды |
| `App.tsx` | `initPlayer` больше не шлёт `orb` (стартовый подарок — default в базе) |
| `lib/skora.ts` | `createSkoraClaim` → RPC, возвращает `{ok, row}` / `{ok, error}` |
| `components/SKORAWallet.tsx` | прямой INSERT убран, локального списания нет |

### Две ловушки, на которых легко ошибиться

**Откат счётчика.** Наивное `setOrb(serverBalance)` теряет тапы, сделанные пока
RPC летел на сервер. Правильно — корректировать на *разницу* между тем, что
сервер подтвердил, и тем, что мы отправили: при согласии коррекция равна нулю и
на экране ничего не дёргается.

**Двойное списание SKORA.** RPC списывает ORB сам, внутри той же транзакции.
Клиент не должен списывать повторно — `onSpendOrb` у кошелька теперь просто
перечитывает баланс с сервера.

Обе проверены в `scripts/orb-sync-test.js` (10 проверок, проходят).

## Порядок выката — по шагам

### 1. Применить SQL (всё выше `PART R`)

SQL Editor → содержимое `supabase-orb-authoritative.sql` до строки `PART R`.

Живой v1.1.4 не ломается: его записи в `orb` будут молча игнорироваться
(0 строк), баланс перестанет расти вверх, ошибок не будет.

Проверка после применения:
```sql
select proname, prosecdef, proconfig from pg_proc
 where proname in ('apply_orb_delta','create_skora_claim');
-- proconfig должен показывать search_path у обеих
```

### 2. Собрать и выкатить APK

```bash
cd android && ./gradlew.bat assembleRelease --no-daemon
```

Проверить на устройстве: тап начисляет; покупка в shop списывает; попытка
потратить больше баланса — отказ и возврат числа; заявка на SKORA списывает
ровно один раз.

### 3. Обнулить Pre-Season (`PART R`)

Только **после** того как новый APK живой — иначе старый клиент запишет
балансы обратно. `PART R` сначала делает снимок в `preseason_snapshot`, потом
пишет обнуление в `orb_ledger` и чистит `tournament_scores`.

## Что осталось открытым

- **Покупные рефиллы обходят лимит энергии.** Дневной потолок 30 млн выбран с
  запасом под это, но если реальный кит упрётся — будет видно в `orb_ledger`,
  и число можно поднять осознанно.
- **Дельта батчится под `reason: 'sync'`**, поэтому отдельный потолок на тап
  (`max_tap`) сейчас не применяется. Чтобы он заработал, надо слать тапы
  отдельным вызовом — это дороже по сети и пока не оправдано.
